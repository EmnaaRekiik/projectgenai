# Correctif API healthcheck — 20 novembre 2026

## Cause exacte

Dans `app/db/session.py`, `get_session_factory()` renvoie un **sessionmaker** (fabrique de sessions). Le code original tentait `with get_session_factory() as session:`, ce qui donne `TypeError: 'sessionmaker' object does not support the context manager protocol`.

Correction appliquée :

```python
def get_db() -> Iterator[Session]:
    factory = get_session_factory()
    with factory() as session:
        yield session
```

## Ce qui a été testé

- 25 tests pytest passent, dont un nouveau test de non-régression `tests/test_db_dependency.py`.
- Le nouveau test appelle `GET /api/v1/health/ready` via la **véritable dépendance** FastAPI `get_db`, sans la remplacer par une fixture ; la fabrique SQLite du test est injectée uniquement à la frontière `get_session_factory`. L'ancienne version échoue à ce test.
- Compilation des modules Python réussie.
- **Limite :** la nouvelle version n'a pas pu être exécutée avec Docker/PostgreSQL dans l'environnement de correction ; le démarrage sur la machine Windows doit encore être validé.

## Redémarrer sur Windows

1. Remplacer les fichiers du projet par ceux de cette archive corrigée, **sans effacer** votre `.env` existant. Vous pouvez aussi remplacer uniquement `app/db/session.py` dans votre dossier actuel.
2. Dans PowerShell, à la racine du projet :

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start.ps1
```

3. Vérifier :

```powershell
docker compose ps
Invoke-RestMethod http://127.0.0.1:8001/api/v1/health/ready
docker compose exec -T api python -m alembic current
```

Résultat attendu pour l'endpoint `ready` : `status: ready`, `database: connected`, `schema: catalogue-v1`. Le résultat de migration devrait afficher la révision `0001_catalogue`.

**Ne pas** lancer `docker compose down -v` : cela détruirait le volume local PostgreSQL. `start.ps1` conserve `.env` et redémarre les services existants.
